## Decisão: Plugin System BeatPlugins-style no CineWeave

**Data:** 2026-07-23
**Área:** CineWeave Plugin System
**Arquitetura:** Map-based registry + React components + API controlada

**Contexto:** CineWeave precisa de extensibilidade sem quebrar código existente. Inspirado no BeatPlugins (https://github.com/lmparppei/BeatPlugins), que usa templates HTML/CSS + JavaScript vanilla.

**Decisão:** Implementar plugin system com:
- Registry Map() simples (4 linhas de código)
- API controlada via useCineWeaveAPI() hook
- React components como templates
- Mínima invasão no código existente (5 linhas adicionadas em App.jsx)

**Por quê:**
- Simples de implementar e manter
- Não afeta performance da aplicação
- Plugins são executados apenas quando necessário (lazy loading)
- Consistente com stack atual do CineWeave (React 19 + Custom CSS)

**Trade-offs:**
- Event system opcional (evita complexidade)
- React components ao invés de HTML templates (mais fácil de debugar)
- API restrita (não permite acesso direto ao estado interno do React)

**Arquitetura escolhida:**
```
src/
├── lib/pluginSystem/index.js      # Plugin registry
├── lib/pluginAPI.js               # API controlada
├── plugins/
│   ├── LinterPlugin.js
│   ├── BechdelPlugin.js
│   ├── CleanerPlugin.js
│   └── templates/
│       ├── LinterTemplate.jsx
│       ├── BechdelTemplate.jsx
│       └── CleanerTemplate.jsx
└── components/
    └── PluginManager.jsx
```

**Integração:**
```javascript
// Linha 15 - Import PluginManager
import PluginManager from './components/PluginManager';

// Linha 23 - Import ícone Cpu
import { ..., Cpu } from 'lucide-react';

// Linha 72 - Adicionar tab Plugins
{ key: 'plugins', label: 'Plugins', icon: Cpu },

// Linha 75 - Estado para modal
const [showPluginModal, setShowPluginModal] = useState(false);

// Linha 151 - Render PluginManager
case 'plugins': return <PluginManager projectId={currentProjectId} />;
```

**Segurança:**
- Plugin API separada com acesso restrito aos dados públicos
- No acesso direto ao estado interno do React
- LocalStorage separado com prefixo `cw_plugin_user_`
- Validação de dados (tratamento de string/texto)
- Sandbox visual com CSS isolado

**Decisões técnicas subsequentes:**
- Map-based registry (simples, não afeta performance)
- React components para templates (stack principal, fácil debug)
- API controlada para segurança (isolamento e validação)
- Pastas separadas para modularização (clara separação de responsabilidades)
- Preservar design system (consistência visual)
- 5 linhas adicionadas (mínima invasão, zero código existente modificado)
- Import direto para PluginManager (pequeno, não vale o overhead de lazy loading)
- Assíncrono (async/await) para não bloquear UI

## Decisão: Python 3.11 venv como **Único** Interpreter para Gateway

**Contexto:** 3 entry-points diferentes disputando o mesmo `gateway.lock`:
- `Hermes_Gateway.cmd` → `miniconda3\pythonw.exe` (Python 3.14.6)
- `Hermes_Gateway.vbs` → `uv-python\cpython-3.11-windows-x86_64-none\pythonw.exe`
- `watchdog.vbs` fallback → `hermes-agent\venv\Scripts\pythonw.exe` (Python 3.11.15)

Resultado: 3 interpreters competindo pelo mesmo `gateway.lock`, gerando `exit_nonzero code=1` em loop.

**Decisão:** Apontar **todos** os entry-points para `venv\Scripts\pythonw.exe`. Miniconda 3.14 uninstalled; uv-python não mais usado para gateway.

**Por quê:** Único interpreter garante que apenas 1 processo detem `gateway.lock`. Resolve race condition sem precisar de redesign maior.

**Trade-off:** Decoupling entre versions Python (uv vs venv) facilitou experimentação — perdemos essa flexibility.

## Decisão: Hermes_Gateway.cmd e .vbs viraram NOOP (workaround contra acesso-denied admin)

**Contexto:** Scheduled Task `Hermes_Gateway` é user-owned (Author: `<DOMAIN>\<user>`) mas não pode ser Disable/Delete sem elevação admin no Windows 11.

**Decisão:** Sobrescrever os 2 scripts (`Hermes_Gateway.cmd` e `.vbs`) com no-op (`exit /b 0` e `WScript.Quit 0`).

**Por quê:** Task continua rodando no logon, mas spawna processo vazio. Não há mais duplicação de gateway spawn duplicado quando outro agente (HermesGatewayAtLogOn, manual user, etc.) inicia.

**Trade-off:** Perpetuamos a task obsoleta em vez de limpá-la. Trade-off aceitável vs admin escalation.

## Decisão: scheduled tasks todas user-owned (sem `-RunLevel Highest`)

**Contexto:** User sem admin no Windows, mas Register-ScheduledTask do proprio user funciona para tasks em `RunLevel = Standard` ou `Interactive`.

**Decisão:**
- `HermesGatewayAtLogOn` (user-owned): user logon → HermeS_Start.vbs
- `HermesGatewayWatchdog_v2` (user-owned): DDI 1 min → hermes-watchdog.cmd
- `HermesGatewayAtStartup` ❌ falhou (precisa admin para `AtStartup`)

**Por quê:** Cobertura 90% via `Logon` + `Shell:Startup\Hermes_Start.vbs`. Trade-offs: Hermes não sobe antes do user fazer login; se user nunca fizer login (server-grade), gateway não sobe.

**Alternativas:** Configurar Windows Service via `nssm` precisaria admin (recusada).

## Decisão: 3 caminhos external_dirs para skills + Travis registry `skills.sh`

**Contexto:** Skills sueltas em 3 paths separados discovered ao longo do uso:
- `%USERPROFILE%\.agents\skills\` — manual + baixadas via `skills.sh add`
- `[CAMINHO]` — projeto OPENCODE (frontend, supabase)
- `%USERPROFILE%\hermes-workspace\skills\` — swarm multi-agent repo + garrytan impl stubs

**Decisão:** Lista-los todos em `skills.external_dirs` em config.yaml. Marketplace principal é `skills.sh` (vercel-labs) via `npx`.

**Por quê:** `get_external_skills_dirs()` em `agent/skill_utils.py` automaticamente combina todos diretorios, salta duplicatas por path, e dedupe por name. Mantem skills custom accessiveis sem duplicar em locais oficiais.

## Decisão: WhatsApp-bridge copiado para venv\Lib\site-packages\scripts\ (path novo 0.19.0)

**Contexto:** Hermes-agent 0.19.0 procura WhatsApp bridge em `venv\Lib\site-packages\scripts\whatsapp-bridge\bridge.js` (não em `hermes-agent\scripts\whatsapp-bridge\` como 0.18.x).

**Decisão:** Copiar o bridge para o novo path esperado pelo 0.19.0.

**Por quê:** 0.19.0 mudou a estrutura de layout. React gateway WhatsApp adapter sem bridge = `fatal: whatsapp_bridge_missing`.

**Trade-off:** Bridge agora duplicado em 2 paths. Cleanup deferred para evitar quebrar Studio legacy que aponta para path antigo.

## Decisão: Boot order = OmniRoute primeiro, depois Gateway

**Contexto:** Gateway lê `OPENROUTER_BASE_URL` do `.env` apontando para `127.0.0.1:20128`. Se Omniroute não estiver up, primeira inference call falha com `APIConnectionError`.

**Decisão:** `hermes-autostart.ps1` espera 3s após start Omniroute antes de start gateway.

**Por quê:** Gateway boot é rapido (~5s) e chamada síncrona de TTS/inference pode acontecer no boot. Se Omniroute nao estiver pronto, gateway log mostra `APIConnectionError` em ciclo.

## Decisão: Watchdog monitora `gateway.health` em 8642 (não só processos)

**Contexto:** Gateway pode estar alive (PID existe) mas sem escutar 8642 (estado degradado).

**Decisão:** `hermes-watchdog.ps1` faz 2 checks: (1) `Is-Gateway-Alive` (process running); (2) `Is-Port-Listening 8642`. Só reinicia se AMBOS são false.

**Por quê:** Pollings só com PID não detecta gateway "zombie" (alive mas unhealthy).

**Trade-off:** Watchdog é complexo (2 checks vs 1 simples). Margem de erro de 30-60s durante boot.

## Decisão: Survey Manager — Supabase direto + lifecycle via updated_at + i18n localStorage

**Data:** 2026-08-21
**Área:** CLIENTE A Survey Manager (dashboard)
**OpenSpec:** changes/survey-manager

**Contexto:** Painel de gestão de pesquisas precisava de CRUD com controle de papel, estados de lifecycle (draft/active/paused/archived) e i18n pt-BR/en.

**Decisão:**
1. Acesso a dados via Supabase client direto (padrão do dashboard), sem rota REST própria — RLS existente (surveys_staff_read / surveys_coordination_write via private.current_campaign_role()) é a fronteira de segurança.
2. Lifecycle paused→archived usa updated_at como marcador de pausa no pg_cron registro, evitando coluna extra; active→paused por end_date.
3. i18n com provider próprio (I18nProvider/useTranslation), fallback locale → pt-BR → chave uppercase + console.warn; persistência em localStorage (desvio do spec registrado na task 3.5, decisão pendente).
4. Arquivamento com confirm() nativo localizado em vez de modal custom.

**Por quê:** reusa convenções do dashboard (getDashboardSupabaseClient/canMutate), minimiza superfície nova e mantém a segurança no banco (RLS), não na interface.

**Trade-offs:** localStorage não sincroniza entre dispositivos (spec pedia profiles.locale); confirm() nativo tem UX limitada; updated_at como marcador de pausa perde precisão se outros updates ocorrerem durante a pausa.

## Decisao: Survey Manager 3.5 - Locale persistido via RPC security-definer (nao UPDATE direto em profiles)

**Data:** 2026-08-27
**Area:** CLIENTE A Survey Manager (dashboard)
**OpenSpec:** changes/survey-manager (task 3.5)

**Contexto:** Spec pedia persistir o idioma em `profiles` (nao so localStorage). Porem `public.profiles` e travada por seguranca: `revoke all ... from anon, authenticated` (20260815260000) seguido de re-grant apenas de SELECT (20260816152000). Voluntarios/outros papeis nao conseguem dar UPDATE direto.

**Options Considered:**
| Opcao | Pros | Contras | Veredito |
|-------|------|---------|----------|
| RPC security-definer `set_my_locale` | Todo papel grava o proprio locale sem expor escrita; funciona em todos os papeis; spec cumprida | RPC extra para manter | escolhida |
| RPC + localStorage primario | Menos escritas | Persistencia fraca entre dispositivos | rejeitada |
| So localStorage | Menor esforco | Nao cumpre a spec | rejeitada |

**Decision:** Migration `20260827200000_survey_locale_persistence.sql` adiciona `profiles.locale text check (pt-BR/en)` e função `public.set_my_locale(p_locale)` (SECURITY DEFINER, `set search_path = public`, self-scoped `where id = auth.uid()`, raise exception em locale invalido/perfil ausente). Grant so de EXECUTE a authenticated. Frontend: `I18nProvider` ganha `initialLocale` + `onLocaleChange`; novo `I18nSyncBridge` adota locale do servidor no load e chama o RPC em mudanca; localStorage vira fallback de boot. `loadCurrentProfile` agora seleciona `locale`.

**Rejected Paths:**
- **UPDATE direto em profiles** rejeitado porque: revoke revogou privilegio UPDATE; re-grant so concedeu SELECT. Expor update direto exigiria RLS/policy ampla, quebrando o lockdown de seguranca de perfis.
- **So localStorage** rejeitado porque: nao cumpre spec `AND the selection is remembered on subsequent visits (persisted to Supabase profiles table)`.

**Consequences:** locale sincroniza entre sessao/dispositivos via servidor; cinco tasks (2.7/2.8/3.5/6.3/3.8-ingles) fechadas; migrations novas exigem aplicacao no Supabase ativo. Pendente: task 3.6 localizar o dashboard inteiro (issue/change separada).
