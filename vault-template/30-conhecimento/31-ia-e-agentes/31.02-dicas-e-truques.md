## Dica: Reiniciar Hermes Gateway limpo (zero stale state)

**Sintoma:** Gateway não subiu, mostra erros de lock, ou duplica processos.

**Fix (PowerShell):**
```powershell
$procs = Get-CimInstance Win32_Process |
  Where-Object { $_.CommandLine -match 'hermes_cli.main.*gateway run' -and $_.CommandLine -notmatch "stop|status" }
foreach ($p in $procs) { Stop-Process -Id $p.ProcessId -Force -ErrorAction SilentlyContinue }

Remove-Item "%USERPROFILE%\AppData\Local\hermes\gateway.lock" -Force -ErrorAction SilentlyContinue
Remove-Item "%USERPROFILE%\AppData\Local\hermes\gateway.pid"  -Force -ErrorAction SilentlyContinue

Start-Process -FilePath "%USERPROFILE%\AppData\Local\hermes\hermes-agent\venv\Scripts\pythonw.exe" `
  -ArgumentList "-m","hermes_cli.main","gateway","run" `
  -WorkingDirectory "%USERPROFILE%\AppData\Local\hermes" `
  -WindowStyle Hidden
```

**Por que:** `gateway.lock` é o arbitrator 1-processo; remover antes de start impede watchdog de confundir com gateway antigo.

## Dica: Verificar Omniroute está rodando

**Sintoma:** `APIConnectionError 127.0.0.1:20128` em loops.

```powershell
netstat -ano | findstr "20128.*LISTENING"

# Se vazio, subir:
Start-Process -FilePath "%USERPROFILE%\AppData\Roaming\npm\omniroute.cmd" `
  -ArgumentList "serve","--no-open","--no-tray","--max-restarts","5" `
  -WindowStyle Hidden

# Ou via status:
& "%USERPROFILE%\AppData\Roaming\npm\omniroute.cmd" status
```

**Alternativa se ?NãoLoga no Login:** Scheduled task falhando — provavelmente foi criada por Studio installer sem admin no Shell:Startup. Workaround: Shell:Startup\OmniRoute_Start.vbs criado manualmente em 24/07/2026 chama `OmniRoute_Start.cmd` em `AppData\Local\hermes\gateway-service\`.

## Dica: Forçar Hermes a releer skills (sem restart)

**Sintoma:** Adicionaste skill em `~/.agents/skills/` mas `hermes skills list` ainda não mostra.

**Fix:** O cache interno (`_EXTERNAL_DIRS_CACHE` em `agent/skill_utils.py:411`) chaveia em mtime do config.yaml. Para invalidar:
```powershell
(Get-Item "%USERPROFILE%\AppData\Local\hermes\config.yaml").LastWriteTime = Get-Date
```
Ou restart gateway (veja Dica 1).

## Dica: Confirmar skills list após install

```powershell
& '%USERPROFILE%\AppData\Local\hermes\hermes-agent\venv\Scripts\python.exe' -m hermes_cli.main skills list
```
Output mostra `Name | Category | Source | Trust | Status` table. Se skill não aparece: restart gateway fixo ou path SKILL.md errado. Cada skill precisa de SKILL.md com frontmatter válido (YAML com `name:` + `description:`).

## Dica: Limpar spread do `npx skills add`

**Sintoma:** Rodou `npx skills add <repo>` e a CLI espalhou para 50+ pastas em cwd (`.claude`, `.devin`, `.grok` etc).

**Fix:** Cmd de limpeza automática — anexar ao `find de skills` workflow:
```powershell
$plane = "[CAMINHO]"
Get-ChildItem $plane -Directory -Force | Where-Object {
  $_.Name -match '^\.' -and $_.Name -ne '.agents' -and (Test-Path "$($_.FullName)\skills")
} | Remove-Item -Recurse -Force
```
Sempre usar `--copy` em vez de `--symlink` para evitar links quebrados em disco.

## Dica: Erro "No module named fcntl" recorrente

**Causa:** `plugins.heartbeat` (POSIX-only). Identificado em 24/07/2026.

**Fix:** Remover `heartbeat` de 4 listas em `config.yaml`:
- `plugins.enabled`
- `plugins.entries`
- `platform_toolsets.cli`
- `known_plugin_toolsets.cli`

Plugin é opcional (keep-alive de sessões), não justifica patch invasivo em Python para win32 (`fcntl` shim seria fragil).

## Dica: Boot script logs -> how to debug flaky boot

**Sintoma:** Após logon ou reboot, gateway pode ter falhado silenciosamente.

**Fix:** Logs auto-start em `AppData\Local\hermes\logs\`:
- `autostart.log` (hermes-autostart.ps1 echoes)
- `autostart-launcher.log` (hermes-start.cmd echoes)
- `watchdog.log` (hermes-watchdog.ps1 echoes)

Inspect:
```powershell
Get-Content "%USERPROFILE%\AppData\Local\hermes\logs\autostart-launcher.log" -Tail 30
Get-Content "%USERPROFILE%\AppData\Local\hermes\logs\watchdog.log" -Tail 30
```

`autostart-launcher.log` mostra toda a chain (pslauncher→cmd→powershell→ps1). `watchdog.log` mostra checks de 1min.

## Dica: User PATH ordering importa — primeiro venv, depois miniconda3 (legacy)

**Sintoma:** `hermes` no PATH chama `miniconda3\Scripts\hermes.exe` (3.14) em vez de `venv\Scripts\hermes.exe` (3.11).

**Causa:** User PATH tem ordem errada; miniconda\Scripts vem antes de venv\Scripts (se não estiver removido).

**Fix:** Verificar e alterar ordem em User PATH:
```powershell
# Remover miniconda entries
$up = [Environment]::GetEnvironmentVariable('PATH', 'User')
$upClean = ($up -split ';' | Where-Object { $_ -notmatch "miniconda" }) -join ';'
# Adicionar venv/Scripts PRIMEIRO
$primary = @(
  '%USERPROFILE%\AppData\Local\hermes\hermes-agent\venv\Scripts',
  '%USERPROFILE%\AppData\Local\hermes\bin'
)
$upOrdered = ($primary + ($upClean -split ';' | Where-Object { $_ -notmatch "hermes" })) -join ';'
[Environment]::SetEnvironmentVariable('PATH', $upOrdered, 'User')
```

System PATH HKLM requer admin — workaround: use o path **absoluto** para python.exe em qualquer script/task.

## Dica: PyInstaller-fork-detection: Python "wrapper" + "worker" sindrome

**Sintoma:** Após start do gateway, vê 2 processos Python em netstat/`Get-CimInstance`:
- PID X `pythonw.exe` em `venv\Scripts\`
- PID Y `python.exe` em `uv-python\cpython-3.11-windows-x86_64-none\`

**Causa:** SEMPRE temos 2 processos (1 wrapper Pythonw + 1 worker Python3 do subprocess). Não são concorrentes — wrapper-e-worker relationship.

**Como distinguir:** Olhe o `Lock` em `AppData\Local\hermes\gateway.lock` — somente 1 PID está gravado. O outro é filho transients no mesmo gateway worker.

## Dica: Scheduled task `-AtStartup` requer admin no Windows 11

**Sintoma:** `Register-ScheduledTask -Trigger (New-ScheduledTaskTrigger -AtStartup)` retorna "Access is denied" mesmo para user logado.

**Workaround:** Use `-AtLogOn -User <user>` task em vez de `-AtStartup`. Cobre reboot+login normal. Para cenários sem login (server), requer admin escalation ou `nssm` install como service.
